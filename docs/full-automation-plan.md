# Full Automation 评估与开发准备

架构规划文档；不包含个人运行实例数据。

## 结论与目标

AutoCanvas 已有可用的自动采集与处理基础，适合进入无人值守可靠性建设阶段。回放链路已有真实成果，直播与异常恢复尚未闭环，不能宣称 Full Automation 已完成。

本计划将 Full Automation 定义为：完成首次配置与必要登录后，自动发现课程及资料、处理媒体、验证产物、恢复可恢复故障，并在确实需要用户介入时给出明确原因；用户关闭 WebUI 不影响运行。验证码等外部身份挑战保留最小人工入口，完成后系统自动继续。

现有范围包括课程、作业正文及附件、直播、回放转写和 Slides。课程公告、通用课件、笔记摘要与搜索作为后续扩展；自动提交作业或代替用户签到不属于本次默认范围。

## 评估范围

本文件保留架构改进方向，已移除个人运行实例的课程、课次、执行统计和日志摘要。部分条目是历史规划，当前实现以源码与测试为准。

## 阻塞 Full Automation 的关键缺口

1. **鉴权状态与故障原因混在一起。** `Auth.session` / `Auth.video` 将广泛异常转成 AuthenticationRequired，网络或平台错误可能被当作需要登录。`/health` 根据历史 needs_login 行判断状态，缺少实际鉴权状态、作用域与检查时间。
2. **鉴权恢复没有自动唤醒。** 登录成功、Cookie 导入成功或静默刷新后，尚无统一机制恢复阻塞任务。`Store.recover` 只恢复 running；周期调度不会重新打开既有回放/直播的 needs_login。
3. **直播发现与录制还未验证闭环。** 查询使用 liveDay=0，默认视频同步间隔一小时，提前十分钟监听只适用于已发现课次。已有事件显示持续失败，缺少可定位阶段、首个音频时间、覆盖率和直播到回放的可靠关联。
4. **重试策略没有区分错误。** 通用异常均按 5/15/60 秒重试，耗尽后回放停在 failed。确定性 TypeError 不会因重复运行消失；长时间网络中断则可能需要更长恢复窗口。
5. **完成状态缺少质量验证。** succeeded 主要表示流程返回；未统一校验产物存在、非空、时间覆盖、清单对应文件。直播检测到关键词仅写事件文件，没有持久化通知投递链路。
6. **常驻运维保障不足。** 当前源码未包含进程托管安装方案、独立存活监测、磁盘预算、缓存回收与持续多日验收记录。运行中的 worker 失败能被报告，但没有自动重建机制。

## 开发顺序

| 优先级 | 功能 | 主要涉及模块 | 完成标准 |
| --- | --- | --- | --- |
| P0-1 | 故障分类与可诊断记录 | auth.py、types.py、service.py、storage.py | 区分登录失效、网络暂态、媒体不可用、程序错误；保存阶段、错误码、脱敏定位信息；复现并修复当前 Slides TypeError |
| P0-2 | 鉴权恢复与任务自动继续 | service.py、browser_auth.py、web_api.py、storage.py | 登录/导入后触发恢复；周期低频探测覆盖 CLI 登录与静默恢复；有效任务只唤醒一次；过期直播触发回放检查 |
| P0-3 | 健康与自动化总览 | http.py、progress.py、OverviewPage.vue | 区分进程存活、调度健康、鉴权状态、阻塞数、最近同步时间与下次恢复动作；历史错误不冒充当前鉴权状态 |
| P1-1 | 直播发现、诊断、回放补偿 | video.py、live.py、service.py | 单独配置发现频率；记录失败阶段与首次真实音频；直播缺口可追踪；回放出现后自动补全 |
| P1-2 | 产物校验与补处理 | flows.py、outputs.py、progress.py | 缺失/损坏产物标记可见并安排有限补处理；空作业结果有明确清单；成功结果不会被失败重试覆盖 |
| P1-3 | 持久化事件与通知 | storage.py、service.py、WebUI | 去重、已读、重试与送达状态；优先站内提示，外部渠道待选定后接入；关键词、阻塞和处理完成均可投影 |
| P1-4 | 常驻服务与资源管理 | CLI、部署配置、配置页 | macOS launchd 托管方案、异常退出恢复、磁盘阈值、缓存保留策略、状态库备份与恢复演练 |
| P2 | 内容能力扩展 | 独立新流程 | 课程资料/公告增量同步；转写与 Slides 对齐、笔记摘要、全文检索；带来源引用和版本信息 |

实现继续遵循当前单向依赖：业务控制留在 Service/流程层，ASR、媒体、Slides 不接入状态数据库；无需引入动态任务注册框架。

## 第一批可实施范围：恢复闭环

建议将 P0-1～P0-3 拆为可独立验证的改动，先有准确故障信号，再接自动恢复，最后呈现控制面。

- **故障模型：** 保留现有执行状态，增加可选的错误分类、失败阶段与安全诊断标识。SQLite 变更应有显式迁移与旧数据兼容；禁止记录完整媒体 URL、Cookie、令牌或原始鉴权响应。
- **恢复入口：** Service 提供统一的鉴权恢复流程。Web 登录/导入成功仅触发它，底层 Auth 不依赖 Store；定时检查处理进程外更新的登录会话。
- **作用域：** Canvas 与课程视频凭证分开判断；Canvas 成功不代表所有课程视频访问成功。对同一作用域合并探测并退避，避免每个阻塞任务重复请求。
- **状态转换：** 当前有效的 needs_login → pending；结束的直播 needs_login → expired，并请求该课程回放同步。cancelled 不自动恢复，succeeded 不自动重跑。
- **控制语义：** 保留 automatic 标记、课程规则及暂停行为。恢复自动任务后，暂停期间仍不能被领取；人工请求维持当前执行语义。
- **诊断：** 给当前 Slides TypeError 增加安全的调用栈位置/阶段信息，在独立测试样本中复现；现有日志只有异常类名，不据此猜测根因。
- **健康输出：** 提供 checked_at、认证作用域、blocked_count、failed_count、最后成功同步时间。健康 GET 读取缓存状态，避免健康探针反复访问学校平台。

必要回归场景：网络超时不变成 needs_login；真正身份失效能阻塞；重复恢复不重复执行；登录恢复后自动继续；CLI 更新会话后可发现；过期直播转回放检查；暂停/课程禁用/显式取消不被绕过；单课程视频异常不阻塞其他课程；健康接口不被历史阻塞记录永久污染。

## Full Automation 验收门槛（目标，尚未达成）

1. 连续运行至少 7 天，关闭浏览器不影响处理；服务退出、网络中断和机器重启后能恢复，记录不可用时间。
2. 对平台已返回且可处理的课次，100% 有明确状态；新增课次在配置的发现周期加调度周期内入队，例外有原因及下一动作。
3. 至少一节真实直播收到音频并完成识别；经历断线重连，记录覆盖率及缺口，并验证对应回放的后续处理。
4. 登录失效产生可见事件；恢复合法会话后，符合条件的任务在两个恢复检查周期内自动继续。
5. 自动化生成的成功记录通过产物一致性检查；没有课程内容时输出明确的空结果，不能返回不存在的产物。
6. 长时间外部故障不会造成无限高速重试；程序错误有可诊断定位，重试耗尽可见，后台 worker 停止可被独立发现。
7. 明确记录处理耗时、ASR 实时率、积压年龄、磁盘占用与直播缺口；不将测试通过等同于识别质量或全天候运行保证。

下一步推荐从 P0-1 开始，并为当前源代码建立可回退的版本基线，再逐项交付恢复闭环。
